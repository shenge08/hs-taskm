# 产品需求文档 (PRD) - HS-TASKM v2.0

## Problem Statement

交易策略开发者面临以下问题：

1. **多语言策略执行环境隔离困难**
   - 交易策略可能使用 Java、Python、Go 等不同语言开发
   - 不同策略需要隔离的运行环境，避免相互干扰
   - 传统虚拟机方案资源消耗大，启动慢

2. **策略配置与代码耦合度高**
   - 策略参数硬编码在代码中，修改参数需要重新编译
   - 数据源和通知渠道与策略逻辑耦合，难以灵活切换
   - 每次调整配置都需要重新构建部署

3. **策略生命周期管理复杂**
   - 缺乏统一的策略启停控制机制
   - 策略运行状态和资源使用情况难以实时监控
   - 策略日志分散，问题排查困难

4. **策略测试与自动化集成困难**
   - 缺乏命令行工具，难以编写自动化测试脚本
   - 无法通过 API 集成到 CI/CD 流程
   - 策略回测和实盘切换成本高

## Solution

HS-TASKM 是一个基于 Docker 的多语言策略容器化执行平台，通过以下方式解决上述问题：

1. **容器化隔离**
   - 每个策略运行在独立的 Docker 容器中
   - 支持多语言策略（Java、Python、Go）
   - 通过 Docker 镜像管理策略运行时环境

2. **插件化架构**
   - 数据插件：代码片段形式，策略运行时调用获取行情数据
   - 监听器：代码片段形式，监听策略产生的交易事件并触发通知
   - 插件/监听器代码存储在数据库中，容器启动时动态注入

3. **任务化执行**
   - 任务是策略的可执行实例，一个策略可以创建多个任务
   - 每个任务对应一个独立的容器
   - 支持任务参数配置、启动、停止、状态查询

4. **RESTful API + CLI**
   - 提供 REST API 供系统集成
   - 提供 CLI 工具供自动化测试脚本集成
   - 支持实时监控容器资源使用和任务执行状态

5. **集中化日志管理**
   - 策略日志写入文件，挂载到宿主机
   - 按任务 ID 和时间戳命名日志文件
   - 保留所有历史日志，支持事后分析

## User Stories

### 1. 策略管理（只读查询）

1.1 作为系统管理员，我希望能够查询所有已注册的策略列表，以便了解系统中有哪些可用策略。

1.2 作为策略开发者，我希望能够按语言（Java/Python/Go）筛选策略，以便快速找到我需要的策略。

1.3 作为策略开发者，我希望能够查看策略的详细信息（名称、版本、Docker 镜像 ID、启用状态），以便了解策略配置。

1.4 作为系统管理员，我希望能够查询策略的 Docker 镜像 ID，以便验证镜像是否已导入。

2.3 作为策略开发者，我希望能够查看数据插件的代码片段，以便了解插件的功能和调用方式。

2.4 作为策略开发者，我希望能够查询数据插件的元数据（名称、语言、启用状态），以便判断插件是否可用。

### 3. 监听器管理（只读查询）

3.1 作为策略开发者，我希望能够查询所有可用的监听器列表，以便了解有哪些通知方式可以使用。

3.2 作为策略开发者，我希望能够按语言筛选监听器，以便找到与策略语言匹配的监听器。

3.3 作为策略开发者，我希望能够查看监听器的代码片段，以便了解监听器的触发逻辑。

3.4 作为策略开发者，我希望能够查询监听器的配置信息（通知类型、配置 JSON），以便了解监听器的行为。

4.5 作为策略开发者，我希望能够为一个策略创建多个任务（使用不同参数），以便对比不同参数的效果。

4.6 作为策略开发者，我希望能够在创建任务时指定任务的名称和描述，以便区分不同的任务。

## Implementation Decisions

### 1. 核心模块设计

#### 1.1 Container Lifecycle Manager（容器生命周期管理器）
- **职责**：封装所有 Docker 操作，提供简洁的容器管理接口
- **接口**：
  - `createContainer(imageId, taskId, config) -> containerId`
  - `startContainer(containerId)`
  - `stopContainer(containerId)`
  - `getContainerStatus(containerId) -> ContainerStatus`
  - `getContainerMetrics(containerId) -> Metrics`
- **实现方式**：使用 Docker Engine API（Java SDK）
- **错误处理**：所有 Docker 操作失败时抛出 ContainerException

#### 1.2 Code Snippet Injector（代码片段注入器）
- **职责**：从数据库读取插件/监听器代码并注入到容器启动配置
- **接口**：
  - `prepareInjection(taskId) -> InjectionConfig`
  - `getInjectionFiles(taskId) -> Map<fileName, content>`
- **注入方式**：通过环境变量传递代码内容，容器内执行引擎读取并执行
- **存储位置**：PostgreSQL TEXT 字段

#### 1.3 Task Orchestrator（任务编排器）
- **职责**：协调任务创建、容器启动、参数传递、状态跟踪
- **接口**：
  - `createTask(taskConfig) -> taskId`
  - `startTask(taskId) -> TaskStatus`
  - `stopTask(taskId) -> TaskStatus`
  - `getTaskStatus(taskId) -> TaskStatus`
- **工作流程**：
  1. 验证策略、插件、监听器存在
  2. 创建任务记录（状态：CREATED）
  3. 调用 Code Snippet Injector 准备注入
  4. 调用 Container Lifecycle Manager 创建容器
  5. 启动容器并更新任务状态（RUNNING）
  6. 启动资源监控

#### 1.4 Resource Monitor（资源监控器）
- **职责**：定期采集容器资源使用情况
- **接口**：
  - `startMonitoring(containerId, interval)`
  - `stopMonitoring(containerId)`
  - `getCurrentMetrics(containerId) -> Metrics`
  - `getMetricsHistory(containerId, timeRange) -> List<Metrics>`
- **监控指标**：CPU 使用率、内存使用量
- **数据存储**：PostgreSQL 时序数据表

#### 1.5 Log Router（日志路由器）
- **职责**：管理日志文件挂载路径和命名规则
- **接口**：
  - `getLogPath(taskId) -> String`
  - `ensureLogDirectory(taskId)`
  - `getLogFileName(taskId, timestamp) -> String`
- **命名规则**：`task_<taskId>_<timestamp>.log`
- **挂载方式**：Docker Volume 或 Bind Mount

### 2. 数据库设计

#### 2.1 核心实体表
- `strategy`：策略表（只读，通过数据库直接插入）
- `data_plugin`：数据插件表（只读，通过数据库直接插入）
- `listener`：监听器表（只读，通过数据库直接插入）
- `task`：任务表（可读写）
- `container`：容器表（可读写）
- `monitor_data`：监控数据表（时序数据）
- `task_log`：日志表（可选，用于日志索引）

#### 2.2 字段说明
- `task.status`：CREATED, RUNNING, STOPPED, FAILED
- `task.parameters`：JSON 格式，存储策略参数
- `data_plugin.code`：TEXT 类型，存储插件代码片段
- `listener.code`：TEXT 类型，存储监听器代码片段
- `listener.config`：JSON 类型，存储监听器配置

### 3. 容器启动配置

#### 3.1 环境变量
- `STRATEGY_PARAMS`：策略参数（JSON 字符串）
- `PLUGIN_CODE`：数据插件代码（Base64 编码）
- `LISTENER_CODE`：监听器代码（Base64 编码）
- `LOG_PATH`：日志文件路径

#### 3.2 卷挂载
- 日志目录：`/var/log/hs-taskm/tasks/<taskId>/` 挂载到容器内 `/app/logs`

#### 3.3 资源限制
- CPU 限制：可选配置
- 内存限制：可选配置

### 4. REST API 设计

#### 4.1 任务管理
- `POST /api/tasks`：创建任务
- `POST /api/tasks/{id}/start`：启动任务
- `POST /api/tasks/{id}/stop`：停止任务
- `GET /api/tasks/{id}`：查询任务详情

#### 4.2 查询接口
- `GET /api/strategies`：查询策略列表
- `GET /api/strategies/{id}`：查询策略详情
- `GET /api/plugins`：查询插件列表
- `GET /api/plugins/{id}`：查询插件详情
- `GET /api/listeners`：查询监听器列表
- `GET /api/listeners/{id}`：查询监听器详情

#### 4.3 监控接口
- `GET /api/tasks/{id}/metrics`：查询任务实时资源使用
- `GET /api/tasks/{id}/metrics/history`：查询历史资源数据
- `GET /api/tasks/{id}/logs`：查询任务日志

### 5. CLI 工具设计

#### 5.1 命令结构
- `hs-taskm task create <strategyId> --params <json>`：创建任务
- `hs-taskm task start <taskId>`：启动任务
- `hs-taskm task stop <taskId>`：停止任务
- `hs-taskm task status <taskId>`：查询任务状态
- `hs-taskm task logs <taskId>`：查看任务日志
- `hs-taskm strategy list`：查询策略列表
- `hs-taskm plugin list`：查询插件列表
- `hs-taskm listener list`：查询监听器列表

#### 5.2 输出格式
- 表格格式（人类可读）
- JSON 格式（脚本解析），通过 `--json` 参数控制

### 6. 策略容器执行引擎

#### 6.1 执行流程
1. 容器启动，读取环境变量
2. 解析策略参数（开始时间、结束时间等）
3. 解码并加载插件代码和监听器代码
4. 进入主循环
   - 检查是否到达开始时间，未到达则空循环
   - 调用插件获取行情数据
   - 执行策略逻辑
   - 产生交易事件
   - 调用监听器处理事件
   - 检查是否到达结束时间，到达则退出
5. 将日志写入 LOG_PATH 指定的文件

#### 6.2 代码执行引擎
- Python：使用 `exec()` 函数动态执行代码片段
- Java：使用 Java Compiler API 动态编译并执行
- Go：使用 plugin 包或 `go run` 动态执行

## Testing Decisions

### 1. 测试原则

#### 1.1 外部行为测试
- 只测试模块的公开接口行为
- 不测试模块内部的实现细节
- 测试用例关注"输入-输出-副作用"，而非代码路径

#### 1.2 测试隔离
- 每个测试用例独立运行，不依赖其他测试
- 使用 Mock 隔离外部依赖（Docker、数据库等）
- 测试后清理所有资源

### 2. 核心模块测试

#### 2.1 Container Lifecycle Manager 测试
- **测试框架**：JUnit 5 + Mockito
- **Mock 对象**：Docker Client
- **测试用例**：
  - 创建容器成功，返回容器 ID
  - 创建容器失败（镜像不存在），抛出异常
  - 启动容器成功，状态变为 RUNNING
  - 停止容器成功，状态变为 STOPPED
  - 获取容器状态，返回正确的状态枚举
  - 获取容器指标，返回 CPU 和内存数据
  - Docker API 超时，抛出 ContainerException
- **覆盖率目标**：> 80%

#### 2.2 Code Snippet Injector 测试
- **测试框架**：JUnit 5 + H2 内存数据库
- **测试数据**：准备插件和监听器的测试数据
- **测试用例**：
  - 任务有插件和监听器，正确生成注入配置
  - 任务只有插件，正确生成注入配置
  - 任务只有监听器，正确生成注入配置
  - 插件或监听器不存在，抛出异常
  - 代码包含特殊字符，正确进行 Base64 编码
  - 生成的环境变量格式正确
- **覆盖率目标**：> 90%（核心业务逻辑）

#### 2.3 Task Orchestrator 测试
- **测试框架**：JUnit 5 + Mockito
- **Mock 对象**：Container Lifecycle Manager, Code Snippet Injector, Repository
- **测试用例**：
  - 创建任务成功，返回任务 ID
  - 启动任务成功，容器创建并启动，状态变为 RUNNING
  - 启动任务失败（策略不存在），抛出异常
  - 启动任务失败（容器创建失败），任务状态变为 FAILED
  - 停止任务成功，容器停止，状态变为 STOPPED
  - 停止任务失败（容器不存在），抛出异常
  - 查询任务状态，返回正确的状态和任务信息
  - 并发启动多个任务，都能成功创建容器
- **覆盖率目标**：> 85%

## Out of Scope

以下功能在本版本中**不实现**，留待未来版本考虑：

### 1. 策略/插件/监听器的创建和管理
- 不提供通过 REST API 或 CLI 创建策略、插件、监听器
- 这些实体通过数据库直接插入管理
- 未来版本可以考虑提供管理界面

### 2. Docker 镜像管理
- 不支持通过 API 拉取或构建 Docker 镜像
- 镜像需要提前手动导入到系统中
- 未来版本可以考虑集成镜像仓库

### 3. 任务调度
- 不支持定时任务调度（如 Cron 表达式）
- 任务只能手动启动
- 未来版本可以集成任务调度框架（如 XXL-JOB）

### 4. 分布式部署
- 本版本只支持单机部署
- 不支持多节点分布式部署
- 未来版本可以考虑引入消息队列实现分布式

### 5. 用户认证和权限控制
- 不提供用户认证和授权
- API 无需认证即可访问（仅适用于内网环境）
- 未来版本可以集成 RBAC 权限控制

### 6. 策略代码的热更新
- 不支持在容器运行时更新策略代码
- 代码更新需要重新构建镜像
- 未来版本可以考虑支持热加载

### 7. 实时日志流
- 不支持通过 WebSocket 或 SSE 推送实时日志
- 日志只能通过文件读取
- 未来版本可以考虑支持实时日志流

### 8. 告警功能
- 不支持任务失败或资源异常的告警
- 监听器代码可以实现告警逻辑
- 未来版本可以考虑内置告警系统

### 9. 数据分析功能
- 不提供策略执行的统计分析功能
- 不提供交易信号的回测功能
- 这些功能属于策略开发者的范畴

### 10. Web UI
- 不提供 Web 管理界面
- 只提供 REST API 和 CLI
- 未来版本可以考虑开发管理后台

## Further Notes

### 1. 设计理念

#### 1.1 简化优先
- 系统设计遵循"简单即美"原则
- 避免过度设计，只实现核心功能
- 优先考虑易用性而非功能完整性

#### 1.2 深度模块
- 核心模块封装复杂逻辑，提供简洁接口
- 模块之间松耦合，便于测试和维护
- 识别并提取可复用的深度模块

#### 1.3 渐进式开发
- 先实现核心功能，再考虑扩展功能
- 每个功能都要有明确的使用场景
- 避免为了"未来可能需要"而增加复杂度

### 2. 技术债务

#### 2.1 已知限制
- 代码片段注入通过环境变量传递，大小有限制（通常 1-2MB）
- 大型插件或监听器代码可能需要改为文件挂载方式

#### 2.2 性能优化空间
- 资源监控数据的存储可以优化（如使用时序数据库）
- 日志文件可以引入索引机制提高查询效率
- 高并发场景下可能需要缓存优化
